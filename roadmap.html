AI Dev Roadmap

The Plan · week by week

Nine weeks from ad hoc prompting to real engineering with Claude Code, across the whole SDLC: planning, building, verifying, tracking, reviewing. One tool for the whole programme, on the Claude Max 5x plan, at 20–25 hours a week. Week 1 wires your environment to a zero-copy-paste bar; week 8 runs the industry's famous methodologies; week 9 merges everything into your own written SDLC methodology. Every week exits with one named deliverable. Each week is one milestone: work the deck, complete the project issues, add the reinforcement. Everything a week needs lives in its weeks/week-N/ folder.

Weeks 1–3 · From prompting to engineering
Week 1

Setup + the map: wire everything

The first inefficiency removed is copy-paste. You wire the lot on day one: gh CLI, MCP connectors to GitHub and your team's systems, a permission baseline, and the token economics of the Max plan you are on. Then the programme map: all four disciplines, each experienced as a one-hour mini-rep. Your friction log starts now: two minutes a day.

  • The agentic loop: chat vs agent, gather → act → verify, reading a session
  • The well-formed brief: role, task, constraints, examples, output
  • Wiring day: gh CLI, MCP connectors (GitHub, DB, docs, tickets), permissions
  • Token economics on Max 5x: windows, caps, model mix, /usage · session triage: /clear, /compact, hand off
  • The four disciplines as mini-reps: context fix · hook · verified loop · parallel run
  • Capstone: environment built to the zero-copy-paste bar + one real automation shipped through it + loop autopsy on the gym repo

Week 2

Context engineering: what the model sees, at the right scope

Every failure you blame on the model is usually a failure of what it was shown. You learn the context window and its attention budget, then the scoping doctrine: global, workspace, project, directory, local. A microservices workspace scopes its docs at the folder spanning the repos; a monorepo scopes at root plus per-package files. The documentation layer (CONTEXT.md, DESIGN.md, guardrails.md) joins CLAUDE.md, and an AGENTS.md symlink keeps your repos agent-portable.

  • Context window anatomy + the attention budget (context is spend)
  • CLAUDE.md as the always-on spec: short imperative rules
  • Scoping doctrine: global / workspace / project / directory / local · AGENTS.md symlink
  • The documentation layer: CONTEXT.md, DESIGN.md, guardrails.md
  • Session hygiene: /clear, /compact, @-refs · agentic search vs pasting
  • Capstone: the scoped docs layer for a real repo or workspace, A/B'd on a 5-task suite, deltas documented

Week 3

Harness engineering: encode it, don't repeat it

The rule of twice: any instruction you have given twice becomes infrastructure, and every piece of it has a correct scope. Allowlists buy safe autonomy, commands capture workflows, hooks enforce guardrails.md, and skills load team knowledge only when relevant. Your harness lands in a codebase you actually work in: the real-repo thread starts here and runs to the end.

  • The rule of twice: repeated instructions become infrastructure
  • Settings + permission allowlists at their scopes: user / project / local
  • Custom slash commands · hooks: guarantees the model cannot skip
  • Skills: progressive disclosure, triggering, project vs personal classification
  • The shared harness: checked-in .claude/ as team infrastructure
  • Capstone: harness v1 in your real repo (settings + 2 commands + 2 hooks + 1 skill, each at its argued scope), raised as a PR

Weeks 4–7 · The engine: plan, loop, graph
Week 4

Planning: spec-driven development

Execution quality is decided before the first edit. You learn when to make Claude think longer, how to move brainstorm → spec → plan → execute, and how to write a spec a cold session can run without asking you anything. Decisions get memory: ADRs written at decision time become context every future session reads, and DESIGN.md stays honest as the architecture moves.

  • Plan mode + extended thinking: when to think longer
  • The pipeline: brainstorm → spec → plan → execute
  • Specs a cold session can run
  • Decision memory: the philosophy of ADRs · DESIGN.md kept honest
  • Plan review beats code review
  • Capstone: one real feature through the full pipeline: spec first, one ADR recorded, shipped

Week 5

Loop engineering I: the verified loop

The first thing this programme never compresses. An agent is only as good as the feedback signal that closes its loop, so you stop trusting "done" and wire typecheck, lint, tests and build as gates. TDD is the tightest loop an agent can run; debugging gets the same shape. Review joins the loop too: Claude becomes first reviewer on every diff, checking changes against your ADRs and guardrails.md before a human ever looks.

  • Never trust "done": typecheck, lint, tests, build as closing signals
  • TDD with an agent: red–green–refactor
  • Debugging as a loop: reproduce → hypothesise → instrument → fix → regression-test
  • Claude as first reviewer: review harness, rubrics, self-review
  • Capstone: TDD a real feature end to end, test-gated; review harness run on its PR + 2 more live PRs, findings vs human review

Week 6

Loop engineering II: autonomy

Once a loop verifies itself, you can let go of it. Headless mode turns Claude into a Unix tool you can schedule and pipe; guardrails plus auto-accept buy unattended hours. The hard lesson is reward hacking: an agent will game a weak signal, so you design signals that cannot be gamed. Autonomy also spends tokens while you sleep, so runs get budgeted against your Max caps.

  • Headless mode: Claude as a Unix tool
  • Long-running loops: checkpoints, auto-accept with guardrails
  • Reward hacking: designing signals agents can't game
  • CI loops: the pipeline heals itself
  • Budgeting autonomous runs on Max: caps, model mix for background work
  • Capstone: an unattended overnight job doing real work, with morning evidence + a cost readout

Week 7

Graph engineering + tracking

A feature is a dependency graph pretending to be a queue. You draw the graph, split the independent branches across subagents and git worktrees, and merge with discipline. Tracking joins in: the epic runs as issues, the gh CLI gives Claude hands on the board, and standups and changelogs come from git truth instead of memory.

  • Work as a DAG: parallel vs serial branches
  • Subagents: context isolation, custom agents, fan-out/fan-in
  • Git worktrees: N sessions, one repo, no collisions · merge discipline
  • Issue-driven development: issue → branch → PR → review as one loop
  • The self-updating board: standups + changelogs from git truth
  • Capstone: a real epic decomposed into a graph, opened as issues, executed across 3+ parallel worktrees, merged clean, board maintained by Claude

Week 9

The merge and the proof

The merge point. Eight weeks of friction log, harness artifacts, specs, loops, rubrics and the steal list become your written methodology: how you plan, build, verify, track and review with Claude Code. Then you prove it twice: onboard a teammate and record what breaks, and ship the proof project, a former fortnight of work delivered in the week, with a retrospective that puts numbers on the change.

  • Standing on giants: merging the steal list with the friction log

  • Rollout: onboarding a teammate, adoption, keeping it alive
