Act 1 · Day 1 · ~50 min

The agentic loop

Act 1 has exactly one idea: an agent is a model in a loop with tools. Tools mean it can read files, edit them, and run commands on your machine — the things you currently do for it. Loop means it repeats a cycle on its own: do something, look at the result, decide the next step. So it gathers its own context, acts on your system, and verifies its own work. The difference between chat and agent isn't intelligence. It's who runs the loop.

Four movements: watch the two workflows side by side and count your hops (M1) · learn the three beats every good turn has (M2) · learn the brief shape that kills the back-and-forth (M3) · then read a real session on the gym repo, beat by beat (Hands-on 01).

In plain words · one lap of the loop, concretely

You tell Claude Code: "the weekly report lists a task twice — fix it." It opens the report code and reads it (gather). It spots the duplicate counting and edits one function (act). It runs your test command and reads the output (verify). The tests pass, so it stops and shows you the diff. If a test had failed, it would have read the failure and gone round again — without you touching anything. That whole cycle, run by the model instead of by you, is the agentic loop. Everything else this week is plumbing to make that loop reach further and safer.

Keep thisOne idea this act: gather → act → verify, run by the agent. Every failure you'll ever debug in this programme is one of those beats done badly.

Under the hood · what a "tool call" actually is

The model can only produce text. So when Claude Code "reads a file", what really happens is: the model writes a structured request — "call the Read tool on src/report.js" — the Claude Code program executes it, and the file's contents come back as text into the conversation. Same for running a command: the model requests the Bash tool, your machine runs the command, and the output (including errors) flows back in. A session transcript is just this exchange repeated: request, result, request, result. That's why you can read any session as a sequence of tool calls — it literally is one.

Act 1 · Movement M3

A well-formed brief kills the back-and-forth

The most practical mindset shift of the week costs nothing to adopt: stop typing requests, start writing briefs. A brief is a prompt with the shape of a spec, and it has five parts: role (who Claude should work as), task (the outcome you want, not the activity), constraints (what must and must not happen), examples (one input → output pair beats a paragraph of description), output (what done looks like, and what proves it). Every part you leave out becomes a round-trip later — Claude asks, you answer — and every round-trip re-sends the whole conversation to the model. why that costs money: Act 3

In plain words · a full five-part brief, worked

Here is the brief the widget's right-hand run uses, line by line:

Role: "You're the release manager for relay's users." — sets the perspective; a release manager writes for users, not for the team.
Task: "Draft release notes covering changes since the last tag." — the outcome. Not "look through the commits", which is an activity.
Constraints: "User-visible changes only; no internal refactors." — the fence. Without it, Claude must guess, and a guess in either direction wastes a turn.
Example: "Fixed: weekly report no longer lists a task twice." — one sample line. This does more than a paragraph about tone, because Claude copies patterns better than it follows adjectives.
Output: "Markdown bullets grouped under Fixed and Added, 80 words or fewer." — what done looks like, checkable at a glance.

Five short lines. Nothing clever in any of them — the power is that nothing is left for Claude to ask about.

Act 2 · Movement M6

MCP: one protocol, every system

Your team's knowledge doesn't live in files. It lives in Notion or Confluence, in Jira or Linear, in a Postgres somewhere, in Sentry. The Model Context Protocol (MCP) is the standard plug for reaching all of it. An MCP server is a small program that speaks for one system: it tells Claude "here are the operations I offer" — search pages, create a ticket, run a query — and Claude can call those operations mid-task, exactly like the file and terminal tools it already has. You connect a server once; every session after that can use it. No server, and you are the integration, ferrying answers by hand.

Under the hood · client, server, and the sign-in

Claude Code is the client. Each connected system runs a server — usually hosted by the vendor (Notion runs mcp.notion.com; you install nothing). When a session starts, Claude Code asks each server "what tools do you offer?" and the answers join Claude's toolbox for that session. When Claude uses one, the request goes to the server, the server does the real work in the real system, and the result comes back as text.

Access is granted through OAuth — the "sign in with your browser" dance you know from "Log in with Google". You approve once in the browser; the server remembers your session from then on. Your password never passes through Claude, and revoking access works the same as for any connected app.

Some servers run locally on your machine instead (started as a background process, called stdio servers) — useful for databases and internal tools that have no hosted option.

Did you know · MCP went from Anthropic project to industry standard in a year

Anthropic open-sourced MCP in November 2024. Within a year OpenAI and Google's Gemini tooling had adopted it too, and the ecosystem passed thousands of community-built servers. That's why it's worth learning as a concept, not a product feature: the connector you configure this week is the same mechanism your next employer's stack will speak, whichever model vendor they use.

Under the hood · reading the hook line, piece by piece

"PreToolUse" is the moment: this hook runs just before every tool call. "matcher": "Bash" narrows it to one tool — terminal commands only.

When the moment arrives, Claude Code runs your command and pipes the pending tool call into it as JSON on stdin (standard input — the stream a program reads when data is piped to it).

jq is a widely used command-line tool for reading JSON. Here it pulls out .tool_input.command — the actual shell command Claude wants to run — and test("push +--force|…") checks it against a pattern of forbidden commands.

The exit code is the verdict. exit 2 tells Claude Code "block this call", and whatever was printed to stderr becomes the explanation Claude sees. exit 0 means "let it through". That's the whole protocol: JSON in, exit code out.
