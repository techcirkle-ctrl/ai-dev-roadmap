In plain words · the four disciplines in thirty seconds

Context engineering controls what Claude can see. Example: a CLAUDE.md file holding your repo's rules, read automatically at the start of every session, so you stop repeating them.

Harness engineering works on the harness, which is everything you configure around Claude: permission rules, hooks, custom commands. It moves the things you keep saying into that equipment, so they happen automatically instead of being retyped.

Graph engineering spots which tasks don't depend on each other, and runs those at the same time instead of one after another.

What is

You use Claude daily.
And you are still the loop's engine.

Be honest about the mechanics of yesterday. You typed a request into a chat box. You waited. You copied the answer into your editor. You ran it. It failed. You copied the error back into the chat. You waited again. Somewhere in there you switched to GitHub, read an issue, and retyped half of it into the conversation for context.

Count the hops. Every one of them was you, carrying text between systems that both sit on your machine. The model reasoned; you did the plumbing.

That workflow has a name: chat-driven development. It treats a coding agent as a very fast colleague you can only reach by post. Every message travels by hand, one exchange at a time. Nothing moves between your replies.

The cost goes beyond minutes. Because every hop passes through you, the loop only runs while you attend to it. Nothing verifies itself. Nothing compounds. Next week's session starts from zero again.

Act 1 · Day 1 · ~50 min

The agentic loop

Act 1 has exactly one idea: an agent is a model in a loop with tools. Tools mean it can read files, edit them, and run commands on your machine: the things you currently do for it. Loop means it repeats a cycle on its own: do something, look at the result, decide the next step.

So it gathers its own context, acts on your system, and verifies its own work. The model's intelligence is the same in chat and agent; what changes is who runs the loop.

  • M1 puts the two workflows side by side, and you count your hops.
  • M2 teaches the three beats every good turn has.
  • M3 teaches the brief shape that kills the back-and-forth.
  • Hands-on 01 has you read a real session on the gym repo, beat by beat.
In plain words · one lap of the loop, concretely

You tell Claude Code: "the weekly report lists a task twice; fix it." It opens the report code and reads it (gather). It spots the duplicate counting and edits one function (act). It runs your test command and reads the output (verify). The tests pass, so it stops and shows you the diff.

If a test had failed, it would have read the failure and gone round again, without you touching anything. That whole cycle, run by the model instead of by you, is the agentic loop. Everything else this week is plumbing to make that loop reach further and safer.

Keep thisThis act has one idea: the agent runs gather → act → verify itself, and every failure you'll ever debug is one of those beats done badly.

M2 · Gather, act, verify

Gather, act, verify: every turn has three beats

GoalLearn to tag any transcript event as gather, act or verify, fast enough that it becomes automatic.

A beat here is a stage in the rhythm, like a beat in a bar of music. Open any good agent transcript and the same three appear.

  • Gather: the model reads files, greps and lists, learning the territory before touching it.
  • Act: it edits, writes, and runs the change.
  • Verify: it runs the tests, checks the output, and compares the result against what was asked.

When a session goes wrong, one beat is missing or done badly. Reading sessions by beat is the diagnostic skill of the whole programme.

Tag every row with its beat. Two rows are traps: one looks like action but is gathering, and the other is the beat most sessions skip.

Under the hood · what a "tool call" actually is

The model can only produce text. So "reading a file" really happens in three moves. The model writes a structured request, such as "call the Read tool on src/report.js". The Claude Code program executes it. The file's contents come back as text into the conversation.

Running a command works the same way. The model requests the Bash tool, your machine runs the command, and the output flows back in. Errors come back the same way. A session transcript is just this exchange repeated: request, result, request, result. That's why you can read any session as a sequence of tool calls; it literally is one.

M3 · The well-formed brief

A well-formed brief kills the back-and-forth

GoalWatch the same task run from a vague ask and from a five-part brief, and count what the vagueness cost in turns and tokens.

The most practical mindset shift of the week costs nothing to adopt: stop typing requests, start writing briefs. A brief is a prompt with the shape of a spec, and it has five parts.

  • Role says who Claude should work as.
  • Task names the outcome you want, rather than the activity.
  • Constraints say what must and must not happen.
  • Examples show the shape: one input and output pair beats a paragraph of description.
  • Output describes what done looks like, and what proves it.

Every part you leave out becomes a round-trip later: Claude asks, you answer. And every round-trip re-sends the whole conversation to the model. why that costs money: Act 3

In plain words · a full five-part brief, worked

Here is the brief the widget's right-hand run uses, line by line.

  • Role: "You're the release manager for relay's users." This sets the perspective; a release manager writes for users rather than for the team.
  • Task: "Draft release notes covering changes since the last tag." This names the outcome. "Look through the commits" would name an activity instead.
  • Constraints: "User-visible changes only; no internal refactors." This is the fence. Without it, Claude must guess, and a guess in either direction wastes a turn.
  • Example: "Fixed: weekly report no longer lists a task twice." One sample line does more than a paragraph about tone, because Claude copies patterns better than it follows adjectives.
  • Output: "Markdown bullets grouped under Fixed and Added, 80 words or fewer." This is what done looks like, checkable at a glance.

Five short lines, and nothing clever in any of them. The power is that nothing is left for Claude to ask about.

The task is to get a release-notes draft out of the relay repo's recent commits. The left run opens with the ask most developers type. The right run opens with five labelled lines. Neither model is smarter; only the brief changed.

Vagueness is expensive: each clarifying question costs a full round-trip, and each round-trip re-sends the whole growing conversation to the model. The vague path literally pays for its own questions.

M6 · MCP: every system

MCP: one protocol reaches every system

GoalSee the clipboard-hop diagram change shape as each connector lands, until the hop count reads zero.

Your team's knowledge doesn't live in files. It lives in Notion or Confluence, in Jira or Linear, in a Postgres somewhere, in Sentry. The Model Context Protocol (MCP) is the standard plug for reaching all of it.

  • An MCP server is a small program that speaks for one system.
  • It tells Claude "here are the operations I offer": search pages, create a ticket, run a query.
  • Claude can call those operations mid-task, exactly like the file and terminal tools it already has.
  • You connect a server once; every session after that can use it.

Without a server, you are the integration, ferrying answers by hand.

Under the hood · client, server, and the sign-in

Claude Code is the client. Each connected system runs a server, usually hosted by the vendor (Notion runs mcp.notion.com; you install nothing). When a session starts, Claude Code asks each server "what tools do you offer?" and the answers join Claude's toolbox for that session. When Claude uses one, the request goes to the server. The server does the real work in the real system, and the result comes back as text.

Access is granted through OAuth: the "sign in with your browser" dance you know from "Log in with Google". You approve once in the browser; the server remembers your session from then on. Your password never passes through Claude, and revoking access works the same as for any connected app.

Some servers run locally on your machine instead (started as a background process, called stdio servers). They're useful for databases and internal tools that have no hosted option.

Did you know · MCP went from Anthropic project to industry standard in a year

Anthropic open-sourced MCP in November 2024. Within a year OpenAI and Google's Gemini tooling had adopted it too, and the ecosystem passed thousands of community-built servers. That's why it's worth learning as a concept rather than a product feature. The connector you configure this week is the same mechanism your next employer's stack will speak, whichever model vendor they use.

Enough diagrams. You'll connect GitHub's official MCP server, then one system your team actually uses. The GitHub server is richer than gh for some reads, and it gives you a clean first OAuth flow. OAuth is the browser sign-in that grants access once.

The commands are two lines. The judgement is in the scope flag, the part of the command that decides who the connection belongs to. It previews a doctrine this programme returns to constantly.

In plain words · user scope vs project scope

Every artifact you add lives at a scope, meaning a level that decides where it applies and who inherits it. That includes an MCP server, a settings file, and later your hooks and commands.

User scope means "mine, everywhere". The config lands in your home directory (~/.claude.json). The server is then available in every project on your machine, and only to you. Right for personal reach: your notes, your GitHub identity.

Project scope means "everyone, here". The config lands in a file inside the repo (.mcp.json) and gets committed. Every teammate who clones the repo then inherits the connection automatically. Right for a team's shared systems: the project's tracker, its docs.

The question to ask each time is always the same: who needs this, me everywhere or everyone here? Today both servers go to user scope; week 2 gives scoping a full treatment.

Permissions: autonomy is a written allowlist

GoalSort real tool calls into allow, ask and deny, then encode the result as your settings baseline.

Wired tools raise the stakes: an agent that can run anything must not run everything. Claude Code's answer is a permission system built on an allowlist. An allowlist is an explicit written list, kept in settings files. It names which commands may run without asking you, which must ask, and which are refused outright.

The lazy failure modes are both bad. Approve-everything fatigue means you stop reading what you approve; ask-me-everything friction means autonomy dies. So the baseline gets engineered once, in a file, and your mood at each prompt stops being the policy.

First calibrate your instincts on the sorter; then encode them. One rule makes sorting fast. Judge the blast radius if wrong, meaning how much damage the worst case does. Ignore how likely the worst case is.

  • Reads can't damage anything, so they're free.
  • Writes inside a git repo are cheap to undo; that's what version control is for.
  • Anything that leaves the machine or destroys state is where "ask" and "deny" live, because there's no undo out there.

Act 3 · Day 3 · ~40 min

Token economics

Three words carry this act, so they get defined now.

  • A token is the unit models read and write text in: roughly three-quarters of an English word ("refactoring" is about three tokens). Everything Claude does is measured in tokens, from every file it reads to every reply it writes.
  • The context window is the model's working memory for one session: your messages, the files it read, and its own replies, all held together.
  • Here is the surprise that makes this an economics act. The model itself remembers nothing between turns, so the whole window is re-sent on every turn. A fat window makes every turn dearer.
  • Last, Claude comes in models you pick between: Opus (most capable, heaviest burn) and Sonnet (fast, the everyday default).

You're on Max 5x for the whole programme, and when it's used daily on real work, its limits will bite. The curriculum treats budgeting as part of the craft.

One honesty up front: a subscription has no price meter. Anthropic shows no dollar figures and no token counts, only usage percentages.

  • The first movement covers the mechanics you can't see directly.
  • Hands-on 05 has you read the meters you can actually read.
  • The last movement covers the three exits from a session that runs heavy.

The register is the same as everywhere: measure, don't trust. "It feels like I have plenty left" is a feeling. /usage and /context are readings.

Did you know · the window holds a long novel

Claude's standard context window is 200,000 tokens. That is roughly 150,000 words, the length of a long novel. That sounds infinite. It isn't.

A handful of large source files, a chatty transcript and some test output eat it faster than you'd guess. Everything in it is re-sent every turn. So a full window is a running cost as well as a limit. That's why the craft of keeping the window lean (week 2) exists at all.

M11 · Session triage

A heavy session has three exits

GoalSort six real moments into clear, compact or hand off, until the choice is reflex.

The meters tell you a session is heavy; they don't tell you what to do. You have three exits.

  • /clear empties the window. It's the cheapest exit, and right whenever the next task doesn't need the history.
  • /compact summarises the conversation in place. It's right mid-task, when the decisions matter but the transcript doesn't.
  • Hand off writes the state to a file that a fresh session reads. It's right when the work continues but this session shouldn't.

The tell is what the history still owes you. If it's done with, clear. If it's needed but bloated, compact. If someone else needs it, including tomorrow's you, hand off.

Two sharp edges.

  • Poisoned context means wrong or misleading text sitting in the window (a bad log, a wrong assumption), quietly steering every later answer. /compact keeps a summary, so poison survives in summary form; a derailed session wants /clear and a restated task, never /compact.
  • Hand off isn't a built-in command. You ask Claude to write the state to a file (done, next, decisions, files touched), then /clear, and point the new session at that file. Week 3 wraps this into a custom /handoff command.
Under the hood · what /compact actually does

/compact asks the model to write a summary of the conversation so far, then replaces the whole transcript with that summary. The window shrinks; the session continues from the summary.

Two consequences follow directly. A summary keeps whatever the model judged important, so give it a focus line and you steer that judgement. And a summary of poisoned context is still poisoned, because the wrong "facts" get summarised right along with the good ones. The mechanism explains the rule.

Widget · the triage sorter

What you decide: your triage habit, written as one line in your notes: "task done → /clear · long task at a breakpoint → focused /compact · day ends mid-work → handoff file." Act 4 · Days 3–4 · ~1.5 h

The four disciplines, once each

Everything this programme teaches lives in four named disciplines.

  • Context engineering controls what the model sees: the files, rules and history in its window decide its behaviour, so you curate them deliberately.
  • Harness engineering works on the harness, meaning everything you configure around Claude (settings, permission rules, hooks, custom commands). The discipline moves what you repeatedly say into that equipment, so it happens automatically.
  • Loop engineering never lets "done" rest on the model's word. You design the work so a machine check closes every loop. That check is a test, or a command with a pass or fail.
  • Graph engineering spots which tasks genuinely depend on each other, and runs the independent ones at the same time instead of in a queue.

Weeks 2 to 7 deepen them one at a time. Today you run all four as mini-reps on the gym repo, so the map is experienced rather than just read.

Harness: a hook is a guarantee

GoalShip one working PreToolUse hook and see it block a command you asked for yourself.

Your permission baseline asks or denies. A hook goes further. It's a small script Claude Code runs automatically at a fixed moment in the loop, for example just before any tool call. The model cannot skip, forget or talk its way past it, because the harness runs it rather than the model.

Written instructions fade as a session grows; code doesn't. In this rep you install a guardrail hook in the gym repo that blocks dangerous git commands, then watch it fire against a live request.

The hook lives at project scope (.claude/settings.json inside the gym repo) because it guards this repo, and anyone who clones it should inherit the guard. That's the scope question from wiring day, answered a second way.

The command below looks dense; the fold under it decodes every piece. Here is the short version. Before any terminal command runs, this script inspects it. A forbidden pattern gets the call blocked, with an explanation Claude can read.

Under the hood · reading the hook line, piece by piece

"PreToolUse" is the moment: this hook runs just before every tool call. "matcher": "Bash" narrows it to one tool: terminal commands only.

When the moment arrives, Claude Code runs your command. It pipes the pending tool call into it as JSON on stdin. Standard input is the stream a program reads when data is piped to it.

jq is a widely used command-line tool for reading JSON. Here it pulls out .tool_input.command, the actual shell command Claude wants to run, and test("push +--force|…") checks it against a pattern of forbidden commands.

The exit code is the verdict. exit 2 tells Claude Code "block this call", and whatever was printed to stderr becomes the explanation Claude sees. exit 0 means "let it through". That's the whole protocol: JSON in, exit code out.

Step 1 — create the hook (requires jq: brew install jq)
Create .claude/settings.json in this repo with exactly:
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "jq -e '.tool_input.command // \"\" | test(\"push +--force|push +-f|rm +-rf\")' >/dev/null && { echo 'guardrail: force-push and rm -rf are blocked in this repo' >&2; exit 2; } || exit 0"
          }
        ]
      }
    ]
  }
}

Capstone · Step 2 · Pick

Pick the automation

GoalChoose one chore from real friction, specify it in a paragraph, and name its verify signal before any building starts.

One real automation, shipped today, used all week. The right pick is boring: a hand-run chore from your actual week, small enough to ship in an hour, frequent enough to feel daily. The wrong pick is impressive: a clever agent pipeline you'll demo once and never run again.

The source is your friction log and the hops you caught yourself doing this week. The spec is one paragraph with four sentences: what triggers it, what it does, what it touches (which wired systems), and what proves it worked. That last sentence is the loop discipline showing up in your planning, three weeks early.

Borrow one if the log is thin:
· Standup writer: yesterday's commits and PR activity (git log + gh) → three-line standup note in your notes file.
· PR describer: current branch diff → PR description with summary, risk notes and test plan, posted via gh.
· Issue triager: new issues on a repo you own → labelled by area, one-line summary comment, via gh.

Capstone · Step 3 · Ship — three moves

Ship it

GoalMake the automation a runnable thing (a script or a slash command) that has run twice and produced its named proof both times.

Build the automation through the wired environment, in three moves. Hand the spec to Claude Code. Make the first run produce its proof. Then run it again untouched. Twice-run is the bar because anything runs once with you hovering; the second clean run is what makes it an automation rather than a transcript.

Move 1: your step-2 paragraph is the prompt. Add only the packaging instruction.

Slash-command packaging, if you chose it: save the prompt as ~/.claude/commands/NAME.md, then it runs as /NAME in any session. That file is a harness artifact at user scope; note the classification, week 3 formalises it.

Move 2: run it for real, on today's real inputs. Then check the proof your spec named. The standup note exists and is true. The PR description is on the PR. The labels are on the issues. Fix what the proof exposes; that's the loop working.

Move 3: run it again on fresh input, touching nothing in between. The second clean run is what makes it shipped. A weekend Application issue asks you to ship a second automation, solo, so keep the friction log warm.

Capstone · Step 4 · Autopsy

Loop autopsy

GoalAnnotate a transcript beat by beat, naming the verify signal that closed the loop (or the vibe that didn't).

One more session on the gym repo, but this time the session itself is the specimen. You'll give Claude a fresh bug and let it work. Then annotate the transcript beat by beat: gather, act, verify. Add a note on what each beat earned. The autopsy habit is how you'll debug every misbehaving session for the rest of the programme.

The specimen task is a bug you haven't touched yet: relay done 2 completes a different task than the one relay list showed as 2. (Two causes conspire; that's what makes the gather beat worth watching.) Give the task, keep your hands off, and take notes per tool call as it runs.
