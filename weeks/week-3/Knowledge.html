Act 1 · Day 1 · ~40 min

The rule of twice

Act 1 has one idea. The first time you give an instruction, it is an instruction. The second time, it is a missing piece of infrastructure, and you have just found it for free.

The skill is not noticing the repeat. Your friction log already lists them. The skill is choosing between the five places a repeat can live. Each one behaves differently, and only two of them can actually stop something happening.

  • M1 shows you the harness you already have, and when each part of it acts.
  • M2 teaches you to route a repeated instruction to the right artifact.
  • Hands-on 01 turns your own friction log into a ranked build list.
In plain words · "artifact" and "infrastructure" here

An artifact this week just means a file you write once and keep. That could be a settings file, a command file, a hook script, a skill folder or a CLAUDE.md.

Infrastructure means the same thing a load-bearing wall means. You stop thinking about it. It holds when you are on holiday, when a new joiner runs the repo cold, and when you are three hours into a bad Friday.

Keep thisThe second time you type an instruction, stop typing it and write the file instead. That single habit is the week.

Under the hood · why only two of the six can actually stop something

CLAUDE.md, skills and commands are text. They enter the window and the model weighs them against everything else there. Strong text usually wins. Usually is not a guarantee.

Permission rules and hooks are code paths in the tool itself. They run outside the model's reasoning, they see the exact tool call about to happen, and their answer is final. That is the difference between asking and enforcing, and it decides which artifact you reach for.

Keep thisText persuades and code enforces. Choose by asking whether you can live with the model deciding not to comply.
M2 · Route the repeat

Every repeated instruction has one correct home

GoalRoute eight real friction-log lines to the right artifact type, and learn the two questions that settle almost every call.

Two questions route nearly everything.

  • Must it be impossible to skip? If yes, it is a hook or a deny rule. If a strong suggestion is fine, text will do.
  • Is it needed always, or only sometimes? Always means CLAUDE.md or settings. Only sometimes means a skill, which loads on relevance, or a command, which loads when you ask for it.

The cost of getting this wrong is real. Rules that only matter occasionally still cost window space every session when you put them in CLAUDE.md. Rules that must never be broken quietly get broken when you leave them as prose.

Call each card below before you read its verdict.

Widget · the artifact router · eight lines from a real friction log

How industry does it · the harness is reviewed like code

Teams that run agents seriously treat the harness as part of the codebase. The command files, hook scripts and skill folders sit in the repo. They get reviewed in pull requests. They change through the same process as production code.

The reason is ownership. A rule that lives on one laptop protects one person. A rule in the repo protects everyone who clones it, including the new joiner who has never heard your speech about the generated files.

Act 2 · Day 2 · ~45 min

Settings and permissions: buying safe autonomy

Act 2 is about the cheapest win of the week. Most of the approvals you answer every day are for commands you would never refuse. Each one costs you a few seconds and breaks your attention, and you pay it dozens of times a day.

The fix is a written list of what is safe here, kept at the right scope, with the genuinely dangerous things named and refused. That is what a permission allowlist is: not a way to stop being careful, but a way to spend your care where it matters.

  • M4 shows how three settings files combine into one effective configuration.
  • M5 teaches you to read permission rules the way the tool reads them, including where they are weaker than they look.
  • Hands-on 02 counts and cuts your own approvals on a real repo.
By the way · the shortcut you will be tempted by

Claude Code has a flag that turns approvals off wholesale. It is spelled --dangerously-skip-permissions and the name is the documentation. It is defensible inside a throwaway container with no credentials and nothing to lose.

Your own machine has your keys, your repos and your production access. There the flag removes the last thing standing between a confused session and a bad afternoon. This week teaches the version that lasts. Name what is safe, refuse what is not, and keep asking about the rest.

Keep thisYou buy autonomy by writing down what is safe, one command pattern at a time. You never buy it by turning the questions off.
M4 · Three settings files, one order

Your settings are three files merged in a fixed order

GoalPredict the effective configuration from three files, and know which keys replace each other and which ones add up.

Settings live in three places, and week 2's scoping doctrine applies unchanged.

  • ~/.claude/settings.json is yours, on this machine, for every project you touch.
  • .claude/settings.json sits in the repo and is checked in, so it applies to everyone who clones it.
  • .claude/settings.local.json sits in the repo but is ignored by git, so it applies to you in this project only.

The more specific file wins. Local beats project, and project beats user. Two behaviours follow from that, and mixing them up is the usual source of confusion.

  • A single value, such as which model to use, is replaced by the more specific file.
  • A list, such as the permission allow list, is added to, so rules from all three files apply together.

Under the hood · what else lives in a settings file

The same file carries more than permissions. Four other keys come up often.

  • model sets which model the session uses.
  • env holds environment variables given to every session.
  • hooks holds the scripts Act 3 teaches.
  • statusLine sets the line at the bottom of your terminal.

There is also a level above all three: an administrator-managed policy file on company-managed machines. It wins over everything, including anything you pass on the command line. If a rule you wrote seems to be ignored on a work laptop, that is the first thing to check.

M5 · Allowlists buy autonomy

A permission rule is read before the model gets a say

GoalRead permission rules the way the tool reads them, and find the cases where a rule you trusted does not match what you meant.

Every tool call is checked against your rules before it runs. There are three answers: allow runs it silently, ask stops and asks you, and deny refuses. Deny always wins, whatever else matches.

Rules name a tool and a pattern, like Bash(npm run test:*) or Edit(./src/**). For shell commands the pattern is matched against the start of the command. So npm run test:* covers npm run test:unit, and everything else that begins the same way.

Under the hood · why a deny rule is not a security boundary

Shell command matching works on the text of the command. A chained command can begin with something you allowed and continue into something you did not. Claude Code makes an effort to split chains, and it will not catch every trick a shell can play.

Treat deny rules as a strong seatbelt against honest mistakes. Honest mistakes are the risk you actually face. A real boundary against a hostile input comes from the environment instead. That means a container, a machine account with no production credentials, or no network at all. Do not ask a text pattern to do a sandbox's job.

Keep thisDeny beats allow, and shell patterns match the start of the command. Allow the dull things by name, and let the rest still ask.

Act 3 · Day 3 · ~55 min

Commands you call by name, hooks you cannot skip

Act 3 covers the two artifacts that change how it feels to work. A command is a prompt you saved under a name, so a workflow you used to retype becomes one word. A hook is a script the tool runs at a fixed moment, and it can stop what is about to happen.

The pairing matters. Commands make the good path easy, and hooks make the bad path impossible. A team that only has commands relies on everyone remembering to use them.

  • M7 shows how a command file expands into the prompt you stopped typing.
  • M8 traces a tool call through the hook events, and one of them gets blocked.
  • Hands-on 03 has you write your own command.
  • Hands-on 04 has you write your own blocking hook.
In plain words · "hook", without assuming you have met one

A hook is a small program you nominate, plus the moment you want it run. The tool runs it at that moment, hands it details of what is happening, and reads what comes back.

Two of those moments matter most this week. Just before a tool call, where your script can refuse. Just after a tool call, where your script can react, for example by running the formatter on the file that was written.

You may have used a git hook that rejects a bad commit message. This is the same idea, one level up. It guards the agent's actions rather than your commits.

Keep thisCommands make the right way the easy way. Hooks make the wrong way impossible. Most repos need both.
M7 · Commands are saved workflows

A slash command is a markdown file that becomes a prompt

GoalRead a command file and predict exactly what the model receives when someone types the command.

A command is a markdown file in a commands folder. Save .claude/commands/release-check.md and you have /release-check in that repo, for everyone who clones it. Save it in ~/.claude/commands/ and you have it in every repo, for you alone.

The body of the file is the prompt. Three pieces of syntax do most of the work.

  • $ARGUMENTS is replaced by everything typed after the command name, and $1, $2 give you the arguments one at a time.
  • A line starting with an exclamation mark runs a shell command first and puts its output into the prompt. The session then starts with real state, rather than a request to go and look.
  • An @ followed by a path pulls that file's contents in.

Under the hood · frontmatter, folders and who may call a command

The block at the top of the file is frontmatter. description is what shows in the command list, and argument-hint tells the reader what to type. allowed-tools limits what the command may do. That limit is what makes the shell prefill safe to grant.

Subfolders become namespaces, so .claude/commands/git/commit.md is /git:commit. That keeps a large team's command list readable.

Claude can also choose to run a command itself when it fits the work. Add disable-model-invocation: true to the frontmatter when a command should only ever run because a human typed it.

M8 · Hooks are guarantees

A hook that exits with code 2 stops the thing from happening

GoalKnow which moment to attach a hook to, and what an exit code of 2 does at each one.

Hooks are configured in a settings file, under the moment you want them to fire. Three moments do most of the work.

  • PreToolUse fires just before a tool call.
  • PostToolUse fires just after one.
  • Stop fires when the session is about to finish answering.

Your script gets the details of the moment as JSON on standard input, and its exit code is the answer. Zero means carry on. Two means refuse. Whatever your script wrote to standard error is handed back to the model, so it knows what went wrong and can try something else.

The same exit code means something different at each moment, which is exactly what the tracer below is for.

How industry does it · the three hooks teams write first

Formatting is the classic PostToolUse hook: every file the agent writes goes through the project's formatter, so style never reaches review.

Protected paths are the classic PreToolUse hook. It guards generated files, lock files, migrations that have already run, and anything carrying a "do not edit by hand" line at the top.

Tests before finishing are the classic Stop hook: the session cannot claim to be done while the suite is red. This is week 5's whole subject, wired here for the first time.

Stuck? · your hook is not firing

Claude Code takes a snapshot of your hook configuration when a session starts, so a hook you add mid-session does not apply to it. Start a new session after editing the config, or add the hook through the /hooks dialogue, which handles the reload for you.

Two other causes are common. The script may not be executable, so run chmod +x on it. The matcher may not match, so check the tool name is spelled exactly as the tool reports it.

Keep thisExit 0 carries on and exit 2 refuses. Choose the moment by what you want: prevent, react, or insist before the session finishes.

Make one mistake impossible, then try to make it anyway

GoalWrite a PreToolUse hook that blocks a real mistake from your own history, and prove it blocks by attempting the mistake.

Pick a mistake that has actually happened in your repo. It could be a hand edit to a generated file, a change to a migration already run, or an edit to a lock file. It could be a write to anything carrying a "do not edit" line at the top.

If nothing comes to mind, week 2 taught you to write these down. Your guardrails.md is a list of never-do rules, and this hands-on turns one of those sentences into something the model cannot ignore. If you have neither, the stand-in repo in this week's data folder ships three planted mistakes to choose from.

Step 1 — write the script
#!/usr/bin/env bash
# .claude/hooks/protect-generated.sh
# Refuses edits to generated files. Exit 2 blocks the call and tells Claude why.
path=$(python3 -c 'import json,sys; print(json.load(sys.stdin).get("tool_input",{}).get("file_path",""))')

case "$path" in
  *.generated.ts|*/dist/*|*/db/migrations/*)
    echo "Blocked: $path is generated or already applied. Edit the source template and re-run the generator." >&2
    exit 2
    ;;
esac
exit 0
file
Save it, then make it executable with chmod +x .claude/hooks/protect-generated.sh. Change the paths in the case statement to the ones that actually matter in your repo.

Stuck? · nothing happens, everything is blocked, no python3

Nothing happens? Start a new session first. After that, check the file is executable and that the matcher covers the tool that was actually used.

Everything is blocked? Your pattern is too broad, and that is a useful failure. Add a line that prints the path to a log file, run once, and read what the hook was actually seeing.

No python3 on the machine? Any language works. The contract is only this: read JSON from standard input, write your reason to standard error, exit 2 to refuse.

Check your read: you have just moved a rule out of your attention and into the repo. It now applies to every session, including the ones your teammates run and the ones that run while you sleep. Act 4 · Day 4 · ~45 min

Skills: knowledge that arrives only when it is needed

Act 4 solves the problem week 2 left open. Your team knows a lot of things that matter occasionally: the migration order, the redaction rules, the way releases are cut. All of it is too long for CLAUDE.md and too important to leave in someone's head.

A skill is a folder with instructions in it. Only its name and a one-line description sit in the window all the time. The instructions themselves load when the work matches the description, which is why a repo can carry twenty of them cheaply.

  • M11 shows what a skill costs before and after it triggers.
  • M12 explains why the description is the whole trigger, and how to place a skill for the team or just for you.
  • Hands-on 05 has you write one skill and test it in both directions.
In plain words · "progressive disclosure"

Progressive disclosure means showing the headline first and the detail only if it is wanted. A restaurant menu lists the dishes; the recipe stays in the kitchen until someone orders.

For skills, the menu line is the description, and the recipe is the instructions file. The model reads the menu every session, at almost no cost, and fetches one recipe when the work calls for it. That is how twenty skills cost you less window space than one long CLAUDE.md section.

Keep thisA skill is knowledge with an address and a trigger. It costs one line while it waits, and a page when it is needed.
M11 · Loaded only when relevant

Twenty skills cost less than one long CLAUDE.md section

GoalSee the window cost of skills before and after one triggers, and compare it against putting the same knowledge in CLAUDE.md.

A skill is a folder containing a file called SKILL.md, plus anything else it needs. Put the folder in .claude/skills/ and the repo carries it. Put it in ~/.claude/skills/ and you carry it everywhere.

The file loads in three stages, and only the first is unconditional.

  • The name and description are read at start-up, for every skill installed. This is a line or two of text each.
  • The instructions in SKILL.md load when the model decides the work matches.
  • Any extra files the skill bundles load only when the instructions send it there, such as a long reference table or a script.

Under the hood · what a skill folder actually holds

SKILL.md starts with frontmatter carrying name and description, and optionally allowed-tools to limit what the skill may do while it runs. Below that is ordinary markdown: the instructions.

Alongside it you can keep anything the instructions reference. A rubric, a checklist, a template, or a script the instructions tell the session to run. None of it costs window space until the instructions send the session to open it. That is the whole reason a skill can be long without being expensive.

Keep thisKnowledge needed in every session belongs in CLAUDE.md. Knowledge needed in some sessions belongs in a skill.
M12 · The description is the trigger

The description is the only part that decides whether a skill ever runs

GoalTell a description that triggers reliably from one that sounds fine and never fires, then place the skill for the team or just for you.

The model never reads your instructions until it has decided to. That decision is made from the description alone, so a brilliant skill with a vague description is dead weight.

A description that triggers reliably does two jobs in one or two sentences.

  • It says what the skill does, in concrete terms.
  • It says when to use it, naming the words, files or tasks that should bring it in.

Then place it. Anything your team needs goes in the repo, where a clone brings it along. Anything that is about how you personally work goes in your home folder, where it follows you and bothers nobody.

Judge each description below before reading its verdict.

Widget · the trigger bench · six descriptions, will it fire?

By the way · the two ways a skill fails

A skill that never fires is the failure you notice, eventually, when someone asks why the migration rules were ignored again.

A skill that fires on everything is the failure you do not notice. It quietly loads a page of irrelevant instructions into sessions that did not need them, and week 2 already told you what that costs. Both failures are fixed in the same place: the description.

Keep thisWrite the description as what it does plus when to use it. If it names no trigger, the skill will not fire.
Hands-on · 05
~20 min

Write one skill, then test it fires and test it stays quiet

GoalShip one skill in your target repo, then prove it works both ways. It must fire on the work it is for, and stay silent on work it is not.

Pick the knowledge your team explains most often to new people, and that only matters sometimes. Migration order, the release routine, how to add a new API endpoint properly, the redaction rules for a sensitive module.

Write it as instructions to a capable colleague who has never seen your codebase. Keep the instructions file short enough to read in a minute, and push long reference material into a separate file beside it.

Step 1 — write the skill
---
name: safe-migrations
description: Use when writing or editing database migrations in db/migrations, including
  column renames, backfills and index changes. Applies our zero-downtime ordering rules
  and the required rollback section.
---

# Safe migrations

Every migration in this repo ships in the order below. A rename is never one step.

1. Add the new column or index, nullable and unused. Deploy.
2. Backfill in batches of 5000, with the batch size in the migration comment. Deploy.
3. Start writing to both old and new. Deploy.
4. Switch reads to the new column. Deploy.
5. Drop the old column, in a separate migration, at least one release later.

Index changes on tables over one million rows use the concurrent form.
Every migration file ends with a rollback section that has actually been run once locally.

Check the finished migration against reference/checklist.md before saying it is done.
file
Save it as .claude/skills/safe-migrations/SKILL.md, replacing every line with your own team's knowledge. Then start a fresh session so the new skill is picked up.
Step 2 — test that it fires
I need to rename the customers.email column to contact_email. Write the migration.
claude
Watch for the skill being used, and check the answer carries your rules rather than generic advice. If it did not fire, the description is the thing to fix, not the instructions.
Step 3 — test that it stays quiet
Add a loading spinner to the settings page while the profile request is in flight.
claude
Nothing about migrations should appear. If the skill fired here, your description is too broad, and it is costing every unrelated session a page of instructions.
Step 4 — record the result
Fill in the table at weeks/week-3/data/skill-trigger-eval-template.md: three prompts that should fire, three that should not, and what actually happened. Rewrite the description and run again until the table is clean.
  • The skill fires on all three prompts written for it
  • The skill stays silent on all three unrelated prompts
  • The answer it produces carries your team's rules, not generic advice
  • You can say why this skill lives in the repo rather than your home folder, or the reverse
Stuck? · never fires, fires constantly, cannot tell whether it fired

Never fires? Put the user's own words in the description. If people say "migration" and "rename", those words belong there. Abstract descriptions of purpose do not match anything anyone types.

Fires constantly? Cut the general clauses. Phrases like "for tasks related to the codebase" match almost every prompt.

Cannot tell whether it fired? Put a distinctive sentence in the instructions, such as a named checklist heading, and look for it in the answer.

Check your read: a skill is not finished when it works once. It is finished when you have evidence in both directions, which is what makes it safe to leave in a shared repo. What you decide: which of your skills belongs to the team and which is yours alone? Write the argument down; the weekend asks for it.
Keep thisTest a skill both ways. Firing when it should is half the test, and staying silent is the half people skip.

M14 · What you commit, what you don't

A harness file has three possible homes, and secrets belong in none of them

GoalSort eight harness artifacts into checked in, kept local, your home folder, or never written into a file at all.

The question is the one week 2 gave you: who suffers if this is in the wrong place?

  • Checked in means everyone gets it and everyone can change it through review. This is where team rules belong.
  • Kept local means .claude/settings.local.json, which git ignores. This is where anything about your machine belongs.
  • Your home folder means ~/.claude/, which follows you across every repo. This is where your personal way of working belongs.
  • Never in a file covers secrets. A hook that needs a token reads it from an environment variable at run time, and the token itself never enters the repo.

Call each card before you read its verdict.

Under the hood · what git should ignore

Claude Code adds .claude/settings.local.json to your gitignore when it first writes one, so the personal file stays personal by default. Check it anyway, because a repository that already had a gitignore can end up with the entry missing.

Everything else under .claude/ is meant to be committed: the shared settings, the commands folder, the hooks folder, the skills folder. Treat that directory the way you treat your CI configuration. It is part of how the repo builds.

Keep thisTeam rules are checked in, machine details stay local, personal style lives in your home folder, and secrets live in none of them.

Someone else clones your repo and runs your harness cold

GoalProve the harness travels: a teammate clones, runs your command, and hits your hook, with no explanation from you.

Everything so far has been tested by the person who wrote it, which is the weakest test there is. This one needs somebody else. A teammate, or another learner on the programme, is fine.

Your only job during the test is to stay quiet. Every question they have to ask you is a gap in the harness, and writing it down is the point of the exercise.

Step 1 — commit the harness
git status --short .claude
git check-ignore -v .claude/settings.local.json
git add .claude && git commit -m "Add harness v1: settings, commands, hooks, skill"
terminal
The second line should confirm that your local settings file is ignored. If it prints nothing, the file is not ignored, so add it to your gitignore before you commit anything else.
Step 2 — hand it over and stay quiet
Ask your partner to clone the branch, start a session, run your command, and then try the mistake your hook is supposed to block. Send them nothing else. No instructions, no explanation, no context.
Step 3 — write down every question they asked
Each question becomes a fix, and most fixes are one line: a clearer command description, a better message in the hook, a line in the repo's CLAUDE.md saying the harness exists. Make the fixes now, while the questions are fresh.
  • Your partner ran the command without asking you anything
  • Your hook refused their attempt, and its message told them what to do instead
  • Your local settings file did not travel with the clone
  • Every question they asked is written down and answered in a file
Stuck? · nobody available, hook fails on their machine

Nobody available today? Clone your own repo into a fresh folder and run it as a stranger, using only what the repo says. It is a weaker test, so book the real one for the weekend anyway.

Hook fails on their machine? Usually a missing tool or an absolute path from your laptop. Use $CLAUDE_PROJECT_DIR rather than a path starting with your home folder, and keep hook scripts to tools every developer on the team already has.

Check your read: a harness that needs its author present is not infrastructure yet. The questions your partner asked are the honest measure of how far it has to go. What you decide: pick the single fix that would remove the most questions, and do it before the capstone.
