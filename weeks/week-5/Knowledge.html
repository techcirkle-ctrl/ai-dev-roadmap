In plain words · what a "loop" means here

Picture reheating soup. You taste it, decide it is still cold, wait a minute, then taste again. Tasting is the signal. Without it you are guessing at a minute and hoping.

An agent works the same way. It makes a change, checks something, then decides whether to keep going. The check is the only part connecting its work to reality.

A loop with no real check is a guess repeated confidently. That is what most chat-driven development actually is.

What is · a Tuesday most of us recognise

It said the tests pass, and nobody ran them

A session that went well, right up until it did not. The repo is an order-sync service: it pulls supplier orders every five minutes, removes duplicates, converts currency, and writes to the database.

  • You asked for retry handling on the supplier fetch. Forty minutes later you had a clean diff and the sentence "all tests pass, the implementation is complete".
  • Nobody ran the tests. Claude ran them nineteen minutes and three edits earlier, so the sentence described code that no longer existed.
  • You merged it. Two days later production duplicated 400 orders, because the retry re-fetched a written batch and the dedupe step used the wrong field.
  • The suite was green throughout. Coverage was 78%, and the dedupe function was covered. No test ever fed it the same order twice.
  • You spent Thursday guessing: three times you thought you had it, changed something, deployed, and waited to see whether the duplicates stopped.

Nothing here failed because of bad code. Every signal in the story reported success, and no signal was ever checked against anything real.

In plain words · what coverage actually measures

Coverage measures which lines ran while the tests ran. That is all it measures. It says nothing about whether anything was checked.

Picture a fire drill where everyone walks past the fire extinguisher on the way out. Coverage reports the extinguisher as covered, because people passed it.

A test that calls a function and asserts nothing gives you full coverage of that function and zero information about it.

What could be · the same change, a week later

The duplicate bug fails a test before it reaches your branch

Here is the same retry work with a verified loop around it.

  • You started red. One test fed dedupe the same order twice and asserted a single row. It failed immediately, which proved the test was real.
  • Claude ran your gate after every change. That is one command running typecheck, lint, tests and build, failing the moment any of them does.
  • On its third attempt Claude tried to loosen the assertion. Your prompt forbade touching the test file, so it fixed the code instead. Act 2 teaches you to expect that.
  • Your review command flagged that the currency conversion used floating-point maths, which contradicts last week's decision record. A human would have to remember that record.
  • You broke dedupe on purpose before merging. The gate went red in 11 seconds, which is the moment you learned it was worth trusting.

The feature was the same size and the hours were similar. What moved is that every claim of "done" had something behind it.

Before we start, rate yourself 1 to 10. Take the repo you work in most. Could you prove your suite catches a real bug rather than assuming it? Could you run a change through a gate that fails when it should? Could Claude review a diff and find something a human missed? Type the honest number. You'll meet it again at the close.

Act 1 · Day 1 · ~45 min

Four checks can close a loop, and each one is blind to something

Act 1 builds the thing the week rests on. A gate is one command that runs every machine check you own and fails if any of them fails. Four checks exist in almost every codebase: typecheck, lint, tests and build.

The point is not to run more checks. It is to know exactly what each check cannot see. A gate you trust for the wrong reasons is worse than none, because it stops you looking.

  • M1 sorts six real defects by which gate catches them. Two are caught by nothing.
  • M2 shows how to find out whether your gate catches anything, by breaking the code on purpose.
  • Hands-on 01 wires your gate into one command, then plants a bug to prove it works.
In plain words · typecheck, lint and build

A typecheck reads your code without running it and complains when a value is used as the wrong kind of thing.

A linter reads your code without running it. It complains about patterns your team has banned, like an unused variable or a promise nobody waited for.

A build turns your source into the thing that ships, and fails when the pieces do not fit together.

Only one of the four checks runs your code at all. That one is the tests, which is why the other three can never replace them.

M1 · Four gates, four blind spots

Every gate catches one shape of mistake, and the worst bugs have no shape

GoalKnow on sight which gate catches which defect, using six real defects from the order-sync service.

Here are the four gates and what each one is actually looking at.

  • Typecheck catches shape mistakes: the wrong kind of value, or a value that might be missing. It never runs your code, so it knows nothing about meaning.
  • Lint catches banned patterns: unused variables, promises nobody waited for, a catch block that swallows an error. These are your team's rules, encoded once.
  • Tests catch behaviour mistakes. This is the only gate that runs your code and compares what happened against what should have happened.
  • Build catches assembly mistakes: a missing dependency, a file that no longer exists, a configuration that does not resolve.

Three of the four never run your code. A bug with the right shapes, allowed patterns and clean assembly sails through all three.

Sort each defect into the earliest gate that catches it. "Nothing catches it" is a real option.

Under the hood · why the worst bug has nothing wrong on the page

Three of the four gates read the text of your program rather than its behaviour. They can only complain about something visibly wrong on the page.

A supplier reference and an order id are both strings, both present, both spelled correctly. The mistake lives in what the value means, and meaning is not visible.

Type systems that let you name a value's meaning catch more. A type called OrderId that cannot be swapped for SupplierRef would catch it. Most codebases stop short of that.

M2 · A gate that never fails is decoration

The only way to know a check works is to break the code and watch it go red

GoalPlant a deliberate mistake, run the gate, and see whether it notices. Here first, your own repo next.

Deliberately breaking working code to see whether the tests notice is called mutation testing. A mutation is one small change that should make a test fail.

  • A surviving mutation means your code can be wrong in a way nothing would tell you about. That is a proven gap, not a style warning.
  • Coverage asks whether a line ran. Mutation asks whether anything would complain if the line were wrong. Full coverage and mostly surviving mutations happen together often.
  • Five shapes cover most of it. Flip a comparison, move a boundary by one, or remove an await. Swap two arguments of the same type, or delete a condition.

You do not need a tool for most of the value. Three mutations by hand, on the module you most fear changing, beats any coverage report.

How industry does it · mutation testing tools, and why they run rarely

The tools are called mutation testing tools. Stryker covers JavaScript and TypeScript, PIT covers Java, and mutmut covers Python.

They generate hundreds of mutations, run the suite against each, and report a mutation score: the percentage killed.

Almost nobody runs them per commit, because running a full suite hundreds of times is slow. Teams run them occasionally on the modules that matter, and treat survivors as a list of missing tests.

Act 2 · Day 2 · ~45 min

The failing test is the instruction. Everything else is a suggestion.

Act 2 is test-driven development: write a test that fails, write the smallest code that passes it, then clean up while it stays green. The three steps are called red, green and refactor.

A failing test is the one instruction Claude cannot misread, argue with or forget halfway through. It is your specification in a form the machine can check. Prose is open to interpretation; a red test is not.

  • M4 runs the same feature down two lanes, test-first against test-after.
  • M5 shows the four things an agent does when a failing test blocks it.
  • Hands-on 02 runs one real cycle on your feature, with the test file off limits.
In plain words · why the order matters at all

Red and green are just the colours a test runner prints. Red means something failed. Green means everything passed.

Write the test after the code and you have never seen it fail. So you have no idea whether it can fail.

Picture a smoke alarm nobody ever pressed the test button on. It looks exactly like a working one. Writing the test first is pressing the button.

M4 · Red first, or green means nothing

A test that has never failed is a test you have not finished writing

GoalStep the same feature down both lanes, and watch what each test actually proves.

Take one job from the order-sync service: dedupe must write one row when handed the same order twice. Build it two ways.

  • Test first: you write the test before the code and watch it fail. That failure proves the test can detect the behaviour being absent.
  • Test after: you write the code, then the test, and it passes immediately. The test was written by reading the code, so it describes whatever the code already does.

If the code has a bug, a test written by reading that code asserts the buggy behaviour and passes. You have locked the bug in and made it harder to fix.

This doubles when Claude writes the test. It has just read the implementation, and it is very good at writing a test that matches what it sees.

By the way · how to get red-first on code that already exists

You cannot write the test first for a function shipped two years ago. So do this instead.

Write the test, watch it pass, then deliberately break the function and check the test now fails. Undo the break.

That gives you the same information as red-first, in a different order. It takes about thirty seconds and it is the cheapest habit in this deck.

M5 · The four ways a test gets weakened

Given a failing test and a deadline, an agent will change the easier of the two files

GoalSpot a weakened test in a diff, using six responses to one failing test.

Give anyone a failing test and pressure to finish, and the test file is the softer target. Humans do this too. Claude does it quickly and describes it as a fix.

  • Weaken the assertion. "Exactly one row" becomes "at least one row". The test still runs and now proves almost nothing.
  • Change the input so the hard case never arises. The two orders get different identifiers, and the dedupe path is never exercised.
  • Skip or delete it, usually with a comment calling it flaky. That word does more work than any other in the vocabulary of not fixing things.
  • Mock the thing under test. The dedupe call becomes a stub returning one row, so the test now tests the stub.

One rule catches all four. If the test file changed while the test was failing, look again. Improve a test before it fails or after it passes, never in between.

Under the hood · why "make the tests pass" invites this week 6 covers it fully

A model produces output that satisfies the goal it was given. If the goal is "make the tests pass", editing the test genuinely satisfies it.

That is a literal reading of a badly worded instruction rather than deception. So the fix is in the wording.

Act 3 · Day 3 · ~45 min

Most debugging is not a loop. It is guessing, repeated quickly.

Act 3 gives debugging a shape: reproduce, hypothesise, instrument, fix, then write a regression test. That last one is a test that fails if this exact bug ever comes back.

Naming the stages makes a wasted move visible. Reading code hoping something looks wrong is not a stage. Neither is changing something to see what happens. Both feel like progress and produce no information.

  • M7 sorts ten moves from a real session into their stages. Four belong to no stage.
  • M8 builds a reproduction from a vague report, and shows why its sharpest form is a failing test.
  • Hands-on 03 drives one real bug through all five stages, with no fix allowed before it reproduces on demand.
In plain words · "instrument" and "hypothesis"

To instrument code means to add something that lets you see what it does while it runs. A log line, a breakpoint, a counter, a timer. Think of it as cutting a window into the side of a machine.

A hypothesis is a statement specific enough to be wrong. "Something is wrong with the sync" is not one.

"The dedupe step receives the supplier reference rather than the order id" is one. You can go and check it, and find out you were mistaken.

M7 · Five stages, and the moves that are guesses

A move that cannot tell you you were wrong is not part of the loop

GoalRecognise a wasted move while you are making it, using ten moves from one real session.

Here are the five stages and the job each one does.

  • Reproduce: make the bug happen on demand, every time. Until then, no fix is testable, because you cannot tell a fix from a quiet afternoon.
  • Hypothesise: write down one specific cause that would produce exactly what you see. It must be specific enough that checking it can prove you wrong.
  • Instrument: add whatever lets you see the thing the hypothesis is about. This turns an opinion into an observation.
  • Fix: change the cause. If you cannot explain why your change makes the bug stop, you have not found the cause.
  • Regression-test: write the test that fails if this bug returns. It is the only stage that changes the future rather than the present.

Anything else is a guess: a move whose outcome cannot tell you that you were wrong. Restarting, skim-reading, changing a value and redeploying, none of them rule anything out.

How industry does it · the same loop, under other names

Scientists call it the hypothetico-deductive method. Doctors are taught it as differential diagnosis. Aviation investigators run it on accidents.

The shared idea is that you do not look for the answer. You propose a cause and then try hard to rule it out.

All three share a rule engineering usually lacks: you may not act on a theory you have not tested. Trying the fix to see if it helps is the move they forbid.

M8 · A reproduction is a recipe

Ten failures out of ten attempts is the moment debugging actually starts

GoalTurn a vague report into a recipe that fails every time, by combining conditions until it fires ten times out of ten.

The report you get is not a reproduction. "Sometimes the sync fails" describes a feeling. A reproduction is a recipe: do these things in this order and it breaks, every time.

  • Without a reliable recipe, a bug that happens once in twenty looks fixed after nineteen quiet runs. That is the worst mistake in debugging.
  • It changes what Claude can do. Given a recipe it can run the failing case and check its own theory. Given a description it can only read code and speculate.
  • A recipe is the cheapest test you will write. The conditions are already worked out, so writing it as a failing test takes two minutes.

The reproduction from this act and the failing test from Act 2 are the same artifact. Reproduce a bug as a test and the fix starts already in the red step.

By the way · shrink the recipe before you theorise

Once you have a recipe that fails every time, start removing parts of it. Take away a condition and run it again.

If it still fails, that condition was never needed. Keep going until every remaining part is load-bearing.

A two-step recipe points almost directly at the cause. A nine-step recipe hides it. This takes five minutes and often finds the bug before you form a hypothesis.

Hands-on · 03
~20 min

Drive one bug through all five stages, with no fix allowed before a reproduction

GoalOne bug closed with all five stages visible, finishing with a regression test that is committed.

Use a live bug if you have one. If not, plant one. Take the module from Hands-on 01 and plant a single mutation on a scratch branch. Then open a session that has never seen the change.

A planted bug is not a lesser exercise. The session genuinely does not know the answer, so the loop runs for real. Friday's capstone does the same. Capture the run on the five-stage sheet at weeks/week-5/data/debug-loop-template.md.

Step 1 — set the rule up front
We are debugging together. Follow this loop and name the stage you are in
before every move:

  reproduce → hypothesise → instrument → fix → regression-test

Hard rules:
- Propose no fix until we have a reproduction that fails every time we run it.
- State every hypothesis as one sentence that could turn out to be wrong.
- Before you change anything, say what you expect to see and why.
- If a move is not one of the five stages, say so and skip it.

The symptom is: <describe it in one sentence, no theories>
claude
Step 2 — reproduce, then write it as a failing test
Work until you have something that fails every time. Run it three times to be sure. Then write it as a test in your suite and watch it go red. Your regression test now exists before the fix does.
Step 3 — one hypothesis, one instrument, one check
Take one hypothesis. Add the log line or counter that shows whether it holds. Run the reproduction and read the output. Rule it out or confirm it before opening a second theory.
Step 4 — fix, then run the gate
Change the cause rather than the symptom, then run /verify. Your new test goes green and nothing else goes red. Remove the log lines you added, then run /verify again.
  • The reproduction failed every time, not most of the time
  • The regression test is committed, not intended
  • You can name the cause in one sentence and explain why the change stops it
  • The instrumentation is removed and /verify is green afterwards
Stuck? · it will not reproduce, it jumps to a fix, you got lucky

It will not reproduce? Widen what you are willing to change. Time, ordering, concurrency and leftover state from a previous run are the usual suspects. State is the most common by far.

It jumps straight to a fix? Stop and ask which stage that move belongs to. The question is usually enough.

Fixed it without a hypothesis? You got lucky. Worth noticing rather than celebrating, because the same luck will not turn up next time.

Check your read: you can name all five stages in order and point at the moment each happened. What you decide: work out what share of the session the reproduce stage took. Most people find it was the longest, and the one they used to skip.
Act 4 · Day 4 · ~45 min

A human should never be the first thing that reads your diff

Act 4 adds the last signal. Before a colleague reads your pull request, Claude reads it against a written list of checks. That list is a review rubric: a file of named questions the reviewer answers about every diff.

This does not replace human review. It makes sure no human spends attention on something a machine could have found. Your reviewer should be arguing about design, not spotting a leftover log line.

In plain words · what a rubric is

A rubric is the list of questions a marker answers about every piece of work. It is written down in advance, so two markers reach the same verdict.

Picture a driving test. The examiner ticks off mirror checks, observation at junctions and the reverse park, from a printed sheet.

That is why a driving test result means something and a general impression does not. Your rubric is that sheet, for diffs.

M10 · A finding needs a place and a rule

Ask for a review and you get prose. Ask against a rubric and you get findings.

GoalTell a finding from noise on sight, using eight review comments where only three are worth your time.

Ask for a review with no further instruction and you get something that reads like a thoughtful review: polite, plausible and almost entirely unusable.

  • A finding names a place: a file and a line. If you cannot go straight there, you will not go at all.
  • A finding names the rule it breaks: your guardrails file, a decision record, the spec. Without a rule, it is one person's taste against another's.
  • A finding names the consequence: what goes wrong if nobody changes it. Without that you cannot decide whether it matters now, later or never.

Strip any one of the three and the comment becomes noise. That is the test you run eight times below, and the shape your own rubric needs.

Sort each finding before you reveal its verdict.

Widget · the findings sorter · eight comments on one pull request

Under the hood · why "review this" produces review-shaped text

Asked to review, a model produces the kind of text that follows the word review. A great deal of what it has seen says "consider adding error handling".

It is producing plausible review-shaped text rather than reading your diff for violations.

A numbered rubric changes the task. Each check becomes a yes-or-no question about a specific file, with no room for a plausible sentence to satisfy it.

M11 · Automate what a human cannot hold

Nobody remembers eleven decision records, and a file reads all of them every time

GoalSee which checks are worth automating, by judging six diffs against two decision records from week 4.

Last week's decision records start paying here. The problem with them has always been that nobody rereads them. Six months on there are eleven, and your reviewer has read two.

  • Human review is good at judgement and bad at recall. A reviewer remembers the records they wrote themselves and misses the rest.
  • A file reads all eleven every time, in about two seconds, and never gets bored on a Friday afternoon. Recall is exactly what to automate.
  • Split it honestly. Machines handle recall: decision records, guardrails, conventions. Humans handle judgement: is this the right thing to build at all.

A machine check reads the letter of a rule and cannot see its purpose. Your rubric should state the reason alongside the rule, which helps without closing the gap.

Judge each diff below against the two records.

ADR-0003 · Money in minor units

All monetary amounts are stored and passed as integers in minor units (pence, cents). Floating-point arithmetic on money is forbidden anywhere in the service. Reason: rounding drift across a 10,000-row batch reconciles to a real, visible discrepancy.

ADR-0007 · No silent catch

Every caught error is logged with its context and then rethrown or explicitly handled. A catch that logs nothing, or logs below warning level, is forbidden. Reason: the 400-order duplication went unnoticed for two days behind a debug-level log.

Widget · the compliance check · six diffs, two recorded decisions

How industry does it · rules as questions, and when to promote one to a lint rule

Keep the rules where the code is, and write them as questions rather than statements. "Does any file under src/fx/ do arithmetic on a non-integer amount?" is checkable. "Money must be handled correctly" is not.

The second habit: when a review keeps flagging the same thing, promote it from a review item to a lint rule.

A rule a machine enforces automatically is cheaper than one a reviewer looks for. That migration is how a codebase gets quietly stricter over years.

GoalThe feature built, with a test written before each piece and the gate run after every change.

Break the feature into two or three behaviours and run a full cycle on each. Do not batch them: one behaviour, one cycle, one gate run.

  • Write every test yourself and watch each fail first. This is the rule abandoned first under time pressure.
